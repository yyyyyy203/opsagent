## 1. 目标与现状

证明 Metrics+Logs 诊断在来源失败、超时、部分返回、案例资格变化和作用域切换时，仍保持证据完整性、审核门禁和记忆隔离。验收必须贯通来源适配器、工具执行管线、父子 Run、SQLite、API、模型输入与浏览器。

2026-10-21 代码盘点基线：

- `test/e2e/memory-multisource-web.spec.ts` 已有一条双来源采集、手动沉淀、审核、同 scope 召回及可选 Trace 限制的正常流程。
- `test/memory-capture-source.test.ts`、`test/memory-case-builder.test.ts`、`test/memory-review-service.test.ts`、`test/memory-recall.test.ts` 已覆盖部分质量、审核、过期和 scope 规则；应复用这些测试并补组合缺口。
- `test/e2e/memory-web.spec.ts` 已覆盖拒绝、撤销和失败调查归档等单来源 UI 行为。
- 多来源夹具的脚本模型主要按成功路径推进，`externalRequestsSent` 固定返回 0；不能直接用它们证明异常传播或服务端无外部请求。
- 现有多 Target 浏览器夹具主要验证工作台隔离，使用无工具的确定性模型；不能直接当作 Target 记忆采集与召回验收。

以上是代码盘点，不是本轮测试通过记录。

## 2. 范围与兼容性

本任务以测试基础设施、适配器组合验收为主，只修复验收实际发现的相关缺陷。所有数据均来自本地模拟 Metrics、Logs；模型使用 ScriptedModel 或等价确定性实现。

不接入在线模型、生产遥测或 LangSmith，不修改或部署 `group-buy-market`。普通 `apps/agent-server` 的 Target Runtime/知识治理接线、Semantic/Procedural 新能力、M2b 迁移、真实动作及性能扩容另立任务。

沿用既有 Event/Message、ToolResponse、MemoryScope、Checkpoint 和 SQLite Schema；预计无需迁移。保留现有记忆状态 `observation | approved | rejected`，过期由 `validUntil` 判定，撤销沿用已有 rejected 语义，不新增状态。

不改变 Harness 顺序、Guard/Hook/HITL 职责、冻结选择和记忆晋级规则。若实现发现必须改变上述边界，先记录 `docs/superpowers/decisions/` 与 `docs/DECISIONS.md`，再修订本 Spec 和计划，不在测试修复中隐式改变语义。

## 3. 行为要求

### 3.1 来源异常与案例质量

1. 故障从来源接口或本地传输边界注入，经实际工具管线生成标准结果；不能直接伪造最终 memory API 响应证明后端行为。
2. Metrics、Logs 的必需来源要求保持由配置决定。单来源失败不得抹除另一来源的可用证据。
3. 缺失必需来源、partial、截断或覆盖不足必须反映到结构化证据、缺失项和案例质量。若终态可沉淀，案例不得成为可批准的 sufficient 参考。
4. 父 Run 可以按现有契约完成部分诊断或失败；测试分别断言终态与证据质量，不强制所有异常变成 completed，也不把 completed 等同于证据充分。
5. 超时和 Abort 在配置预算内结束。检查取消信号、调用次数上界、终态及资源释放；不能靠测试超时终止进程来证明正常取消。
6. 分页已接收的有效数据发生后续错误时，应依现有证据契约保留可用部分并明确 partial/限制。不得把部分数据标成完整；若现有链路不支持预期保留行为，应先记录差异并评估兼容性。
7. Trace 不在 requiredSources 时，缺口作为限制保留，不覆盖完整 Metrics+Logs 的质量；列为必需来源时仍受缺失证据门禁。

### 3.2 审核、有效期与召回

1. 候选默认 observation；质量不足、失败/取消来源 Run 或无效证据的批准请求必须由后端拒绝，不能只禁用 UI 按钮。
2. 合格模拟案例可人工批准为历史参考，始终 `eligibleForPromotion=false`。
3. 未审核、拒绝、撤销或已过期案例不进入后续 Run 的 hints 和实际模型输入。到期条件沿用 `validUntil <= now` 不可用。
4. 已批准案例在新 Run 同 scope、相同查询下必须有正向召回对照，排除关键词、预算或错误配置导致的假阴性。
5. 冻结选择仍按已有规则重校验；撤销/过期后不能通过重新扩大检索恢复该案例。复用相关机制测试，不引入新的运行中选择策略。
6. UI 展示应与当前 API 状态一致，并能说明不可审核或不可用的原因；不要求将已过期 approved 案例重写为新的持久化状态。

### 3.3 作用域与证据引用

1. 多 Target 验收在同一个临时 SQLite 中保存案例，使用相同检索问题和可匹配症状；数据库分离不构成隔离证明。
2. Target 身份和 scope 由宿主配置、可信绑定及冻结快照派生，不从浏览器字段或模型文本构造可信身份。
3. 浏览器覆盖 A 的案例在 A 可召回、B 不召回；服务与 dataset 维度以同库集成测试逐项改变验证，避免一次改变所有字段掩盖过滤缺陷。
4. 案例证据引用须回查到正确父子 Run 的原始证据与摘要/哈希；跨 Target 读取或审核必须按现有边界拒绝。
5. 不能用伪造候选、直接 SQL 修改审核状态或 mock 掉 scope 过滤来证明闭环。单元测试的独立夹具不受此端到端限制影响。

## 4. 测试夹具设计

### 4.1 场景与生命周期

场景至少包含正常、Metrics 失败、Logs 失败、来源超时、Logs 分页中断/截断。场景是测试侧有限枚举，配置在 Run 启动前冻结；不得在活跃 Run 中切换全局场景影响其他用例。

每个独立用例拥有独立临时目录、运行标识、统计和时钟。一个隔离用例内部的 A/B 刻意共享数据库。场景重置前须等待或取消全部活跃 Run 并释放来源资源；异常启动和 teardown 也要关闭 HTTP/MCP、数据库、游标/快照和临时文件。

测试控制面只监听 loopback，使用严格输入校验及每次启动的控制凭证；不注册为 Agent Tool，不进入模型上下文，不加入产品 API。

### 4.2 确定性模型与时钟

脚本模型检查 ToolResult 的成功、错误和证据引用，执行有界分支；失败时不得无限重复同一调用，也不得无条件声称双来源成功。

通过既有 Clock 注入能力控制业务时间，采集窗口随场景时钟生成。有效期推进只在受控步骤进行；超时/Abort 测试使用实际可取消调用和明确的短预算，不能用推进业务时间替代传输取消验证。

记录模型收到的案例 ID、证据标记或可断言的消息投影；“模型是否使用记忆”的证明来自实际输入，而非最终自然语言回答或夹具自报成功。

### 4.3 请求观测

替换固定为 0 的外部请求字段：实际记录受测浏览器及服务端传输边界的请求、目标和拦截结果，允许列表仅包含本次创建的本地端点。外部目的地在连接前拒绝，观测器以不会发出网络请求的禁止目的地测试自证有效。

浏览器请求日志不代表 Node 进程的全部出站请求。验收必须列明覆盖的 fetch/HTTP/MCP 等实际调用入口、允许的 loopback 请求及未覆盖范围；只在观测覆盖范围内声明零外部发送。

## 6. 完成标准与交接

每个 ID 必须对应具名测试、本次命令结果及证据；失败、跳过、未覆盖范围必须明示。核心断言检查结构化结果、引用、错误码、持久化状态及模型输入，UI 文案只作补充。

实施完成须通过计划规定的核心/Web 检查、记忆验收、多来源和 Target 浏览器回归；完成验收报告并更新 STATUS。按阶段独立提交推送，遇阻记录实际原因，不能把 Spec 或计划写成即视为实现完成。
